## 1 项目目标

### 1.1 一句话目标

为有竞赛组队需求的学生提供一个数字社区。每名学生拥有一个由本人控制、了解本人能力和近期状态的数字分身；学生可以用自然语言向数字分身表达参赛或组队意图，数字分身在授权范围内代为提交申请、发布招募、关注匹配机会、与其他数字分身进行受控沟通、汇总候选人并协调约谈时间，最终组队决定始终由学生本人作出。

### 1.2 要解决的问题

学生参加竞赛时，通常难以及时了解有哪些比赛、哪些队伍正在招募、谁的能力可以互补、谁近期有时间投入。现有组队方式依赖熟人关系、群聊刷屏或临时询问，信息分散，重复沟通多，也容易因能力、目标和时间不一致导致组队失败。

本项目让学生把组队意图直接告诉数字分身，由数字分身代为完成重复的信息整理、机会关注、初步沟通和时间协调。数字分身帮助主人减少搜索和沟通成本，但不得替主人作出最终承诺。

### 1.3 数字分身定义

数字分身是绑定到学生账户、由学生本人维护和控制的 AI 组队代理，不是独立用户，也不是可以自行承担责任的主体。

数字分身可以使用以下三类信息：

- 本人档案：本人确认的技能、项目经历、擅长方向、竞赛偏好和期望分工。
- 近期状态：当前是否找队、已有队伍情况、近期任务负荷、可投入时间和可沟通时间。
- 当前授权：主人针对某次竞赛、招募、自动关注或分身沟通明确授予的操作和信息使用范围。

数字分身产生的公开内容、消息和操作必须能够追溯到所属学生账户。数字分身不得虚构主人信息，不得使用未授权信息，不得代替主人确认组队或报名。

### 1.4 核心价值

- 自然表达意图：学生不必逐项填写复杂流程，可以直接告诉数字分身自己想参加什么比赛、能做什么和需要什么队友。
- 自动关注机会：数字分身持续关注已上线竞赛、队伍招募和能力需求，在主人授权范围内主动发现匹配机会。
- 减少重复沟通：数字分身之间先围绕技能、分工、目标和近期时间进行初步交流，再向各自主人反馈。
- 支持组队决策：队伍负责人的数字分身汇总多个候选人，生成带理由和不确定项的候选队员排行榜。
- 协调真人沟通：主人选定候选人后，数字分身交换已授权的可用时间，提出双方均可选择的约谈时间。
- 保留人工决定：公开发布、最终约谈时间、正式队伍邀请、接受邀请和竞赛报名均由相关学生本人确认。

### 1.5 核心业务闭环

竞赛上线子流程：学生向数字分身表达参赛意图 → 数字分身发现平台尚未收录该竞赛 → 数字分身整理并提交竞赛收录申请 → 平台管理员审核 → 审核通过后竞赛上线。

智能组队主流程：队伍负责人向数字分身说明组队目标和成员需求 → 确认后由数字分身创建队伍并发布招募 → 其他学生数字分身持续关注并判断能力、目标和近期时间是否匹配 → 符合条件的数字分身联系队伍负责人的数字分身 → 双方数字分身进行受控初步沟通 → 分别向主人反馈 → 队伍负责人的数字分身生成候选队员排行榜 → 主人选择希望进一步了解的候选人 → 数字分身协调约谈时间 → 双方主人确认时间并进行真人沟通 → 双方本人确认后建立队伍成员关系。

## 2 用户角色与使用场景

### 2.1 MVP1 用户角色

按照课程要求，MVP1 设置且只设置以下三种业务角色：

1. 普通参赛学生：维护本人数字分身和近期状态，授权数字分身关注竞赛与招募、发起初步联系，接收数字分身反馈，并自主决定是否进一步沟通或加入队伍。
2. 队伍负责人：向数字分身表达组队需求，确认队伍与招募发布，查看候选队员排行榜，选择候选人，确认约谈时间和正式队伍邀请。
3. 平台管理员：审核竞赛收录申请，直接创建可信竞赛，维护已上线竞赛，停用失效竞赛，并查看关键操作审计记录；不参与普通组队决策。

工程实现时，账户层只区分学生账户和管理员账户。队伍负责人是学生在具体队伍范围内获得的权限，不是独立账户类型；同一名学生可以在一支队伍中担任负责人，在其他队伍中作为普通成员。

数字分身不是第四种用户角色，而是代表所属学生执行获准操作的系统代理。

### 2.2 场景一 维护数字分身和授权范围

学生首次使用系统或个人情况变化时，维护以下信息：

- 基础资料：昵称、专业或年级等组队所需信息。
- 能力资料：技能、项目经历、擅长方向和可承担分工。
- 竞赛偏好：感兴趣的竞赛类型、比赛目标和期望角色。
- 近期状态：是否找队、已有队伍情况、当前任务负荷和近期可投入时间。
- 沟通时间：主人愿意接受约谈的日期和时间段。

学生可以开启或关闭“自动关注”和“分身主动联系”。开启后，数字分身只能针对主人选择的竞赛方向、能力范围和信息可见范围开展活动。关闭后，数字分身不得继续发起新的自动联系。

### 2.3 场景二 通过数字分身提交竞赛收录申请

学生可以直接告诉数字分身自己想参加的竞赛。数字分身先查询平台是否已经存在该竞赛；如果不存在，则根据学生提供的信息整理竞赛名称、官方信息来源、报名时间和简介，向主人展示申请摘要。主人确认后，数字分身提交竞赛收录申请。

新申请的初始状态为“待审核”，不会直接公开。平台管理员可以将申请标记为“已上线”或“已拒绝”，也可以直接创建可信竞赛。管理员可以更新已上线竞赛，并将失效竞赛标记为“已下线”。只有“已上线”的竞赛可以创建队伍和发布招募。

MVP1 的竞赛状态只包括“待审核”“已上线”“已拒绝”和“已下线”。

### 2.4 场景三 通过数字分身发起组队

学生可以用自然语言告诉数字分身准备参加的已上线竞赛、本人能够承担的工作、队伍目标、需要的成员方向、预计投入时间和计划人数。

数字分身将意图整理为结构化的队伍和招募摘要，向主人展示。主人确认后，数字分身才可以创建队伍并发布招募。数字分身不得根据模糊意图自行补充未确认的比赛目标、成员要求或工作量承诺。

### 2.5 场景四 数字分身主动关注和联系

队伍招募发布后，已开启自动关注的其他学生数字分身可以根据以下信息判断是否可能匹配：

- 招募需要的技能和分工。
- 学生本人确认的能力与经历。
- 双方的竞赛目标。
- 学生近期任务负荷和可投入时间。
- 学生当前是否已有冲突队伍或任务。

达到基本匹配条件后，候选学生数字分身可以在预授权范围内主动联系队伍负责人的数字分身，不要求主人逐条批准首次联系。数字分身只能披露主人已经授权用于组队匹配的信息。

### 2.6 场景五 数字分身受控沟通

两个数字分身可以围绕当前招募进行简短的多轮沟通，用于确认：

- 队伍当前成员构成和仍缺少的方向。
- 候选学生能够承担的工作和相关经历。
- 双方的竞赛目标、项目进度和预期分工。
- 双方近期可投入时间。
- 仍需要真人确认的问题。

MVP1 中，每组数字分身针对同一招募和候选人最多进行三轮往返，双方各最多发送三条消息。达到轮数上限、确认明显不匹配、获得足够信息或任一主人关闭授权后，对话必须停止。

数字分身不得在对话中接受队伍邀请、承诺最终分工、承诺固定工作量、确定最终约谈时间或完成竞赛报名。对话内容必须留存审计记录，并能标明使用了哪些授权信息。

### 2.7 场景六 向主人反馈并生成候选队员排行榜

数字分身完成初步沟通后，分别向各自主人的站内消息中心反馈。

候选学生收到的信息至少包括：队伍当前情况、能力与时间匹配点、不匹配或不确定项、数字分身沟通摘要和建议进一步确认的问题。

队伍负责人收到的信息至少包括：候选人的相关能力、近期时间、竞赛目标、沟通摘要、匹配理由和待确认问题。当存在多个候选人时，队伍负责人的数字分身生成候选队员排行榜，即本项目所称的“PK”。

排行榜必须展示评分维度、排序理由、缺失信息和不确定项，不得只给出无法解释的总分。MVP1 只允许使用与组队直接相关且由学生授权的信息进行排序，不得使用性别、家庭情况等与组队无关的敏感信息。排行榜只提供建议，最终候选人由队伍负责人选择。

### 2.8 场景七 数字分身协调约谈时间

队伍负责人选定希望进一步了解的候选人后，可以让数字分身协调约谈。双方数字分身只交换主人已经提供并授权用于约谈的可用时间段，计算共同时间，并分别向主人提出候选时间。

只有双方主人明确确认同一时间后，系统才创建站内约谈记录。MVP1 不直接接入外部日历、会议或即时通信服务；系统只记录约谈时间和双方确认状态。

### 2.9 场景八 真人确认队伍关系

真人沟通后，队伍负责人可以确认发出正式队伍邀请，候选学生可以接受或拒绝。只有队伍负责人和候选学生分别作出明确操作后，系统才建立队伍成员关系。

数字分身可以提醒主人处理邀请并整理已有沟通信息，但不得自动发出正式邀请、自动接受邀请或自动确认组队。建立队伍成员关系不等于完成正式竞赛报名。

## 3 MVP1 边界

### 3.1 MVP1 功能白名单

MVP1 只覆盖以下五项核心能力：

1. 数字分身与意图代办：学生维护数字分身、近期状态和授权范围，并通过自然语言要求数字分身整理竞赛收录申请或组队招募；公开提交或发布前必须由主人确认。
2. 竞赛收录与队伍招募：平台管理员审核竞赛收录申请；已上线竞赛允许学生通过数字分身创建队伍并发布招募。
3. 主动关注与受控沟通：获得预授权的数字分身根据能力、目标和近期时间主动发现匹配机会，并围绕一项具体招募进行最多三轮往返的初步沟通。
4. 双向反馈与候选排行榜：数字分身分别向主人反馈沟通结果；队伍负责人的数字分身对多个候选人生成可解释的排行榜、匹配理由和待确认问题。
5. 约谈协调与人工确认：数字分身根据双方授权的可用时间提出约谈时间；最终时间、正式队伍邀请、接受邀请和建立成员关系必须由相关学生本人确认。

未列入上述白名单的业务能力不默认属于 MVP1。新增能力必须先修改本文件并经过小组确认，再进入后续 Spec、Issue 和开发流程。

### 3.2 MVP1 最小演示闭环

演示至少准备一项待审核竞赛、一名队伍负责人和三名拥有不同技能与近期状态的候选学生及其数字分身。

完整演示流程包括：

1. 学生要求数字分身提交竞赛收录申请，主人确认后提交。
2. 平台管理员审核通过，竞赛进入已上线状态。
3. 队伍负责人向数字分身说明组队需求，确认后发布队伍招募。
4. 至少三名候选学生的数字分身关注到招募并完成匹配判断。
5. 至少两名符合条件的数字分身主动联系队伍负责人的数字分身并完成受控沟通。
6. 候选学生收到各自的匹配反馈；队伍负责人收到候选队员排行榜、排序理由和待确认问题。
7. 队伍负责人选择至少一名候选人，双方数字分身提出共同可用的约谈时间。
8. 双方主人确认约谈时间；真人沟通后分别确认正式邀请和接受邀请。
9. 系统建立队伍成员关系，并能够查看上述关键操作的审计记录。

只展示聊天界面、数字分身形象、比赛列表或静态排行榜，但无法完成上述闭环，不视为完成 MVP1。

### 3.3 数字分身权限边界

| 行为 | 可自动执行 | 需要主人确认 | MVP1 禁止 |
| --- | --- | --- | --- |
| 读取已上线竞赛和公开招募 | 是 | 否 | 否 |
| 使用主人已授权的档案和近期状态进行匹配 | 是 | 首次设置授权时确认 | 否 |
| 提交竞赛收录申请 | 否 | 提交前确认 | 否 |
| 创建队伍并公开发布招募 | 否 | 发布前确认 | 否 |
| 发现匹配机会并联系其他数字分身 | 开启授权后可以 | 开启或变更授权时确认 | 否 |
| 围绕具体招募进行最多三轮往返沟通 | 开启授权后可以 | 开启或变更授权时确认 | 超出范围或持续自主沟通 |
| 向主人发送匹配反馈和提醒 | 是 | 否 | 否 |
| 生成候选队员排行榜 | 是 | 否 | 自动淘汰或自动选择候选人 |
| 提出双方共同可用的约谈时间 | 是 | 否 | 自动确认最终时间 |
| 发出正式队伍邀请 | 否 | 队伍负责人确认 | 自动发出 |
| 接受队伍邀请并建立成员关系 | 否 | 候选学生确认 | 自动接受或自动确认组队 |
| 完成正式竞赛报名 | 否 | 由本人在相应渠道操作 | 数字分身代为完成 |

### 3.4 信息授权与审计边界

- 学生必须能够查看和修改数字分身使用的本人档案、近期状态和对外可见信息。
- 自动关注和主动联系默认关闭，由学生主动开启，并可随时关闭。
- 数字分身只能围绕具体竞赛和招募使用与组队直接相关的信息。
- 数字分身不得向其他用户或数字分身披露未授权联系方式、学号或其他私人信息。
- 所有竞赛申请、招募发布、分身间消息、排行榜生成、时间建议、正式邀请和确认操作必须留下审计记录。
- 审计记录至少能说明操作主体、所属主人、发生时间、操作类型、关联竞赛或队伍，以及是否经过本人确认。

### 3.5 MVP1 完成判定

当团队能够使用准备好的演示数据，以平台管理员、普通参赛学生和队伍负责人三种业务角色完成“自然语言表达意图、数字分身代办、管理员审核、主动关注、分身受控沟通、双向反馈、候选排行榜、时间协调和真人确认组队”的端到端演示，并能查看关键操作审计记录时，MVP1 的业务闭环成立。

具体页面、字段、接口、匹配算法、排行榜权重、消息格式和逐条验收标准由后续 Spec 定义，本文件不替代 Spec。

## 4 Non-Goals（非目标）

以下内容不属于 MVP1。若要做，必须先修改本章并经过小组确认，禁止在开发过程中“顺手实现”。

| 编号 | 非目标 | 边界说明 | 重新评估条件 |
| --- | --- | --- | --- |
| NG-01 | 不做数字分身“人格/形象/语音”产品化 | 不做 3D 形象、语音对话、性格养成、独立分身账号；分身只是绑定学生账户的代理 | 核心闭环稳定演示后，由小组单独立项 |
| NG-02 | 不代学生完成正式竞赛报名 | 报名始终由本人在官方渠道操作，系统最多记录“已提交报名”状态 | 不做；即使后续接入也必须逐次本人确认 |
| NG-03 | 不接外部日历、会议、IM、短信、邮件 | 不做腾讯会议/飞书/Zoom 预约、微信/QQ/钉钉通知、短信验证码、邮件发送；站内消息与站内约谈记录即为全部沟通渠道 | 课程明确要求接入时再评估 |
| NG-04 | 不做开放社交社区 | 不做动态、点赞、评论、关注博主、陌生人私信、组队广场刷屏 | 不做 |
| NG-05 | 不做推荐算法与模型训练 | MVP1 匹配为可解释的规则打分（技能命中、目标一致、时间可行、冲突检查）；不做向量召回、协同过滤、模型微调、训练管线 | 规则打分无法区分候选时，先加维度再考虑召回 |
| NG-06 | 不做自动淘汰、自动组队、自动邀请、自动接受 | 排行榜只做建议；任何成员关系变动必须双方本人操作 | 永久不做 |
| NG-07 | 不做信誉分/历史战绩画像 | MVP1 不引入跨竞赛的信用评分、评分互评、黑名单评价体系 | 有真实多竞赛数据后另立规格 |
| NG-08 | 不做文件上传与简历解析 | 不解析 PDF/图片简历，不存附件；能力信息以结构化字段录入 | 结构化字段不足时再评估 |
| NG-09 | 不做多端 | 只做响应式 Web；不做小程序、原生 App、桌面端 | 不做 |
| NG-10 | 不做多语言与主题定制 | 仅中文界面，固定浅色主题 | 不做 |
| NG-11 | 不做实名认证与学籍校验 | 不做学信网/校园统一身份对接、身份证 OCR、人脸识别 | 课程要求时再评估 |
| NG-12 | 不做支付、会员、广告、数据变现 | 无任何收费链路 | 不做 |
| NG-13 | 不做运营后台全家桶 | 管理员仅具备审核、创建/编辑竞赛、下线竞赛、查看审计 | 不做 |
| NG-14 | 不做微服务、高可用、水平扩展、消息队列 | 单后端进程 + 单库即可；不引入 Redis/Kafka/ES/对象存储 | 演示完成后若继续演进再讨论 |
| NG-15 | 不做实时推送 | 不用 WebSocket；消息中心以轮询/手动刷新呈现 | 轮询体验不可接受时再评估 |
| NG-16 | 不做数据大盘与导出报表 | 不做出入参统计、转化漏斗、CSV 导出（审计查看除外） | 不做 |

## 5 技术栈与硬性技术约束

### 5.1 技术选型结论

**选定：前端 Vue3 + Vite + TypeScript；后端 FastAPI + Pydantic + SQLModel + SQLite。**

依据：

1. 仓库 `pyproject.toml` 与 CI 已按 Python 锁定（fastapi、uvicorn、pydantic、sqlmodel；ruff/mypy/pytest），沿用现有骨架零迁移成本。
2. 前后端分离让 6 人按契约并行：3 人后端、2 人前端、1 人流程与文档（兼验收与 E2E），互不阻塞。
3. 项目是“重流程”：`domain`（状态机/权限矩阵）+ `services`（流程编排）+ `api`（薄路由）的分层正好承载审核、招募、受控沟通、排行榜、约谈与审计。
4. Pydantic 契约 + FastAPI 自动 OpenAPI，前端类型由契约生成，减少接口漂移。
5. 单进程 + SQLite，第 15–16 周答辩现场风险最低。

选型约束：MVP1 不引入第二套服务端框架或全栈框架，也不并行维护两套数据访问层；技术栈如需变更，必须走第 8 周 ADR-001 并先修改本文件，进入第 10 周后不再换栈。

### 5.2 硬性技术约束

以款为强制项，代码评审时逐条检查；与本文冲突的 AI 产出必须退回修改。

| 编号 | 约束 |
| --- | --- |
| TC-01 | 架构：单 FastAPI 后端进程 + 单 Vue3 前端工程 + SQLite；不拆微服务，不引入消息队列、缓存中间件、对象存储、搜索引擎。 |
| TC-02 | 数据库：开发与演示统一使用 SQLite 单文件，通过 SQLModel 访问；`models.py` 是数据模型唯一真源；所有业务写操作必须在同一 Session/事务内完成，异常回滚，不允许部分成功。 |
| TC-03 | 业务规则只在应用层实现，禁止用数据库触发器、存储过程、视图承载流程判断。 |
| TC-04 | 所有状态变化必须经过显式状态机（枚举 + 转移表）校验；禁止任何“直接 UPDATE 状态字段”的写法；非法转移统一返回拒绝并写审计。 |
| TC-05 | 权限必须在服务端强制校验：所有路由通过 FastAPI `Depends` 统一按“会话/身份 → 账户类型（学生/管理员）→ 队伍内角色 → 本次操作的授权范围”四步校验；禁止只在前端隐藏按钮，也不能只靠前端拦截。 |
| TC-06 | 审计表为 append-only：只允许插入与查询，禁止提供 UPDATE/DELETE 接口，禁止物理删除；审计写入与业务写入同一事务，审计失败即业务失败。 |
| TC-07 | 数字分身一切外发内容（收录申请、招募、分身间消息、反馈、排行榜、约谈建议）必须经服务端“授权字段过滤 + 数量/轮次上限”校验后才可落库或展示。 |
| TC-08 | 模型调用只在后端进行；密钥仅存在于服务端环境变量，禁止出现在 `web/` 代码、前端构建产物或 `VITE_` 前缀变量中。 |
| TC-09 | 模型输出必须解析为结构化 JSON 并通过 Pydantic 模型校验后才可进入业务；解析或校验失败时重试至多 1 次，仍失败则降级为规则模板并标记“待主人确认”，禁止把自由文本直接当作业务数据。 |
| TC-10 | 所有“确认类”操作（提交申请、发布招募、确认约谈时间、发出邀请、接受邀请）必须携带一次性确认令牌或幂等键，服务端去重，重复请求只返回首次结果。 |
| TC-11 | 时间统一以 UTC 存储、按 Asia/Shanghai 展示；约谈可用时间使用“日期 + 时间段”模型，粒度 30 分钟，禁止存自由文本时间。 |
| TC-12 | 排行榜必须逐项落库：维度、各维度得分、权重、数据来源、缺失项、不确定项、排序理由；禁止只存总分或只在前端计算排序。 |
| TC-13 | 前端不得重算匹配分、排序、轮次剩余数等业务值，一律以接口返回为准，避免出现两套真源。 |
| TC-14 | 分身沟通的轮次与条数计数由服务端持久化维护，客户端不可修改；达到上限后服务端拒绝新消息，不做“前端置灰”式限制。 |
| TC-15 | 隐私：不采集性别、家庭情况、身份证、健康等与组队无关的信息；联系方式不落明文展示；档案与近期状态支持学生查看、修改、关闭展示。 |
| TC-16 | 自动关注与主动联系默认关闭，授权可随时关闭；关闭后必须立刻阻断新的自动联系，已发起的会话不得继续自动发送。 |
| TC-17 | 演示可运行性：`python scripts/run_dev.py` 一条命令完成建库、seed 与前后端启动（内部执行 `uvicorn` 与 `npm run dev`）；不得要求 Docker、Redis、MySQL 等外部安装；seed 可重复生成且结果稳定（固定随机种子）。 |
| TC-18 | 接口契约以 `src/contest_team/schemas/` 下的 Pydantic 模型为唯一真源，OpenAPI 由 FastAPI 自动生成；前端类型由 OpenAPI 生成，禁止手写重复的请求/响应类型；改接口必须先改 schema。 |
| TC-19 | 核心流程必须有自动化测试：pytest（httpx）覆盖状态转移矩阵、权限矩阵、三轮/三条上限、审计写入、幂等去重与接口；Playwright 覆盖 3.2 的九步演示闭环；CI 的 lint + typecheck + test 全绿方可合并。 |
| TC-20 | 性能基线：演示数据规模（≤100 学生、≤20 竞赛、每招募 ≤50 候选）；不含模型调用的接口 P95 < 1s，模型调用超时 30s 并有降级路径；页面首屏在本地环境 < 3s。 |
| TC-21 | 运行环境：Chrome / Edge 最新版，桌面优先，最小适配 1280×720；不承诺移动端完整体验。 |
| TC-22 | 依赖管理：新增任意第三方包必须在 PR 中说明用途与必要性，并经小组确认后合入；禁止“为方便”批量引入工具库。 |
| TC-23 | 代码结构：流程判断只允许出现在 `domain/` 与 `services/`；`api/` 只做依赖注入、Pydantic 校验、调用与返回；页面与组件不得直接访问数据库，不得写状态流转。 |
| TC-24 | 数据模型变更必须通过 Alembic 迁移脚本入库（Alembic 于第 9 周前按 TC-22 接入；接入前只允许用 `scripts/reset_db.py` 重建，禁止手工改表）；演示前 7 天（第 14 周起）冻结模型，冻结后只允许修数据不改结构。 |
| TC-25 | 单仓协作：共享文件（`models.py`、`domain/*`、`schemas/*`、`pyproject.toml`、前端基础组件）由对应 owner 修改，其他人须经 owner 同意后合入；每人独占自己的 `services/<module>.py` 与页面目录。 |
| TC-26 | 前端只通过 HTTP 访问后端；后端 `domain/`、`services/` 不得 import `api/` 或 FastAPI 的 `Request`；服务端配置与密钥不得进入 `web/`。 |
| TC-27 | 读走 GET、写走 POST/PATCH：写路由必须声明权限依赖、Pydantic 入参校验与幂等键（TC-10）；路由函数内不得直接操作数据库，跨模块写入一律经 service。 |

### 6.2 依赖准入规则

- 任何新增依赖必须同时说明：用途、是否为唯一可选方案、是否引入外部网络、是否影响离线演示。
- 允许范围内的基础库（后端 fastapi、uvicorn、pydantic、sqlmodel、alembic、pytest、pytest-cov、httpx、ruff、mypy；前端 Vue3、Vite、Pinia、Vue Router、Vitest、Playwright、openapi-typescript）视为已批准；其余一律按 TC-22 走确认。
- 模型供应商只允许通过一个统一适配接口接入（可用环境变量切换 mock 模式）；演示必须支持“无模型模式”，用规则模板产出等价的演示效果。
- 引入任何依赖后，必须保证 TC-17 的一键启动仍然成功，否则回退。

## 7 技术风险与应对方案

| 编号 | 风险 | 触发信号 | 影响 | 应对 | 兜底 |
| --- | --- | --- | --- | --- | --- |
| R-01 | 模型输出不稳定、幻觉或凭空补全主人未确认的信息 | 返回非 JSON、字段缺失、出现档案里不存在的经历 | 招募/反馈失真，违反 1.3 | 结构化 schema 校验 + 字段白名单（TC-09）；prompt 只喂授权字段；对外内容一律经主人确认 | 降级为规则模板，标注“待确认”，演示走 mock 模式 |

| R-04 | 6 人并行导致接口漂移与合并冲突 | 字段对不上、同一文件多人改动 | 联调时间被吃掉 | `schemas/`（OpenAPI）为唯一契约并生成前端类型（TC-18）；模块所有权与文件独占（5.2、TC-25）；每日同步 + 每周固定集成窗口 | 以契约为准回退他人改动，冲突由模块 owner 裁决 |
| R-05 | AI 生成代码绕过流程规则（直接改状态、跳过审计） | PR 出现裸 UPDATE、路由层写分支、无审计写入 | 闭环不成立，验收失败 | TC-04/TC-06/TC-23 作为评审清单；核心规则目录由流程负责人在评审中把关 | 相关 PR 拒绝合入，规则文件由负责人手改 |
| R-06 | 状态机漏分支、非法转移未拦截 | 出现“待审核”直接跳到成员关系等异常状态 | 演示流程断裂 | 转移表穷举 + 非法转移统一拒绝并审计（TC-04）；状态机单测覆盖全部状态对 | 演示前跑状态矩阵测试，失败即阻断发布 |
| R-07 | 排行榜被质疑“黑箱”或使用了敏感信息 | 只显示总分、排序理由缺失 | 与 2.7 要求冲突，评审扣分 | 维度/权重/来源/缺失项全部落库并展示（TC-12）；权重集中配置；敏感字段在打分入口即拒绝 | 关闭自动排序，仅展示并列候选与人工选择 |
| R-08 | 隐私与授权争议（学生不愿公开某些信息） | 用户反馈“没授权却被展示” | 合规与信任风险 | 默认关闭自动关注（TC-16）；档案/状态可查看、可修改、可关闭；最小化采集（TC-15） | 全局关闭对外展示，仅本人可见 |
| R-09 | 演示现场失败（网络、模型超时、数据被改乱） | 模型 30s 无响应、账号状态异常 | 无法完成闭环演示 | 一键重置 seed（TC-17）+ 固定演示脚本 + mock 模型模式 | 切换录屏备份，按脚本逐步说明 |
| R-10 | 时间协调格式混乱（时区、跨天、粒度不一） | 提议时间无法对齐、重复时间段 | 约谈环节卡住 | UTC 存储 + 时间段模型 + 30 分钟粒度（TC-11）；共同时间由服务端计算 | 由负责人手动指定时间段并记录 |
| R-11 | 性能塌陷：模型串行调用拖慢页面 | 消息中心/排行榜打开 > 5s | 演示观感差 | 模型调用异步化、状态轮询、结果落库缓存、超时降级（TC-20） | 全部切换 mock 模式演示 |
| R-12 | 数据模型反复变更导致返工 | 演示前仍在改表结构 | 阻塞前端与测试 | 迁移脚本入库 + 演示前 7 天 schema 冻结（TC-24） | 冻结后以补丁表或计算字段兜底，不改主表 |
| R-13 | 团队对“分身能做什么”理解不一致 | 有人实现自动邀请/自动接受 | 越过 3.3 权限边界 | context.md 作为唯一依据，3.3 表格逐条对照评审 | 争议项一律按“需主人确认”处理 |

| 队伍 / 队伍负责人 | Team / Team Owner | 队伍为竞赛下的组队单元；负责人是学生在具体队伍范围内的角色，不是独立账户类型 |
| 招募 | Recruitment | 队伍公开发布的成员需求说明，含所需方向、目标、投入时间与计划人数 |
| 候选学生 | Candidate | 被招募匹配到、可能加入队伍的学生 |
| 匹配判断 | Match Evaluation | 分身依据授权信息对技能、目标、近期时间与冲突情况做的可解释判断 |
| 双向反馈 | Two-way Feedback | 沟通结束后分别向候选学生与队伍负责人推送的匹配反馈 |
| 候选队员排行榜（PK） | Candidate Ranking | 队伍负责人的分身对多个候选人生成的可解释排序，只作建议 |
| 约谈 | Interview / Meetup | 真人沟通环节；系统只记录时间与双方确认状态，不接外部日历会议 |
| 正式队伍邀请 | Team Invitation | 队伍负责人本人确认后发出的邀请 |
| 成员关系 | Membership | 候选学生接受邀请后建立的队伍成员身份；不等于完成竞赛报名 |
| 审计记录 | Audit Log | 对关键操作的追加式记录，含主体、主人、时间、类型、关联对象、是否经本人确认 |
| 状态机 | State Machine | 以枚举与转移表定义合法状态变化的机制，所有状态变更必须经其校验 |
| 幂等键 | Idempotency Key | 确认类操作的一次性令牌，用于防止重复提交与重复副作用 |
| 契约 | Contract | 由 `src/contest_team/schemas/` 的 Pydantic 模型定义的请求/响应结构，经 FastAPI 生成 OpenAPI；前端类型由 OpenAPI 生成，禁止重复定义 |
| 降级模式 | Fallback Mode | 模型不可用或输出不可解析时，改用规则模板产出等价结构，并标注待确认 |
| APIRouter / Depends | — | FastAPI 的路由层与依赖注入：负责鉴权、校验、调用 service 与返回结果，不承载业务规则 |
| 演示闭环 | Demo Loop | 3.2 所列九个步骤可完整走通并可查看审计记录的最小可验收路径 |
| Non-Goal | 非目标 | 明确排除在 MVP1 之外的内容，未改本文件不得实现 |
