# agent-rules.md
> 文件定位：项目级 AI 协作统一规则（全工具兼容）
> 适用范围：Claude Code / Cursor / GitHub Copilot / 所有 AI 编程辅助工具
> 生效状态：待小组评审确认
> 最近更新：2026-11-02

---

## 一、总则
### 1.1 规则定位
本文件是本项目所有 AI 代理与 AI 辅助开发场景的**强制协作契约**，优先级高于所有 AI 工具的默认行为逻辑。所有 AI 生成代码、修改文件、输出技术方案前，必须完整读取并严格遵守本规则。

### 1.2 边界对齐
- 业务边界、MVP 范围、非目标以项目根目录 `context.md` 为准；本规则与 `context.md` 冲突时，以 `context.md` 为准。
- 架构决策以 `adr/` 目录下的正式 ADR 文档为准，AI 不得擅自突破已确认的架构方案。

### 1.3 核验原则
本规则所有条款均要求**可执行、可检查、可在 PR 评审中逐条核验**，禁止模糊性表述与口号式要求。

## 二、项目专属业务红线（强制执行，零容忍）
> 本章节为项目核心业务底线，所有代码实现必须严格遵守，任何突破均视为无效 PR。

### 2.1 数字分身核心行为禁令
1. **严禁自动确认核心决策**：任何业务逻辑中，不得实现数字分身自动确认组队、自动接受队伍邀请、自动发布招募、自动提交竞赛报名、自动确认约谈时间的功能；所有最终生效操作必须保留显式的人工确认节点，代码中必须存在独立的人工确认校验逻辑，不得存在跳过人工确认的执行路径。
2. **对话轮次强制封顶**：同一招募场景下，两个数字分身之间的双向对话最多允许 3 轮往返（双方各发送最多 3 条消息）；代码中必须内置轮次计数器与强制终止逻辑，达到轮次上限后必须自动结束对话并提示人工介入，禁止无限制自主对话。
3. **信息使用严格授权**：数字分身仅可使用用户已明确授权的档案、状态与业务数据；不得虚构用户信息、不得使用未授权数据、不得向其他分身/用户披露非公开的隐私信息。
4. **禁止自主决策排序**：候选队员排行榜仅可输出匹配维度、排序依据与不确定项，不得由数字分身自动淘汰候选人、自动选定最终成员；所有组队决策必须由真人操作触发。

### 2.2 审计日志强制规范
1. **全操作留痕**：数字分身的所有关键操作（消息发送、匹配计算、排行榜生成、约谈时间协调、竞赛申请提交、招募发布、授权范围变更）必须生成完整审计日志，日志必填字段：
   - 操作主体：所属用户唯一标识
   - 操作类型：明确对应业务动作
   - 关联业务ID：对应竞赛/队伍/招募/对话ID
   - 操作时间：精确到秒的时间戳
   - 人工确认标记：该操作是否经过用户显式确认
   - 操作内容摘要：核心行为的不可篡改描述
2. **日志不可篡改**：审计日志必须写入独立存储，业务代码仅提供日志写入与查询能力，严禁提供编辑、删除、修改日志的接口与逻辑。
3. **异常操作可追溯**：所有越权尝试、规则拦截、异常终止的场景，必须同步记录审计日志并标注异常原因。

## 三、仓库与文件操作规范
### 3.1 目录访问权限
严格遵循项目标准化目录结构，仅允许在对应目录内开展操作：
- 正式业务代码：仅可在 `src/` 目录下对应模块内编写与修改，禁止擅自新增顶层目录。
- 需求与架构文档：仅可在 `spec/`、`adr/` 目录下新增对应文档；根目录核心文件 `context.md`、`agent-rules.md` 未经小组评审，禁止修改。
- 技术探针代码：仅可存放于 `docs/spike/` 目录，严禁混入 `src/` 正式业务代码。
- 测试代码：必须存放于 `tests/` 目录，与 `src/` 目录结构保持一一对应。

### 3.2 文件修改禁令
- 无明确指令时，禁止修改根目录下的 `context.md`、`agent-rules.md`、`README.md` 等核心配置与规则文件。
- 禁止修改其他模块的公共依赖、全局配置与基础组件；若需修改，必须在 PR 中明确说明架构影响并标注评审标签。
- 禁止删除项目标准目录结构与核心占位文件。
- 禁止在项目中引入未在技术约束中明确的第三方依赖与服务。

## 四、代码编写与架构约束
### 4.1 分层与职责约束
- 严格遵循分层架构规范：接口控制层、业务逻辑层、数据访问层职责分离；数字分身核心业务规则必须收敛在业务逻辑层，禁止在控制层直接实现业务校验逻辑。
- 通用业务规则（授权校验、轮次限制、审计日志生成、人工确认校验）必须封装为独立的中间件/拦截器/工具类，禁止散落在各业务代码中。
- 数字分身的行为逻辑与业务状态解耦，核心规则可配置、可统一校验。

### 4.2 命名与编码规范
- 命名必须与业务术语保持一致（术语表参考 `context.md`），禁止使用无意义缩写与模糊命名；数字分身相关实体统一使用 `Agent` 前缀，审计日志相关实体统一使用 `Audit` 前缀。
- 变量、函数、类名遵循项目统一的语言命名规范，保持代码风格一致性。
- 核心业务红线对应的代码段，必须添加行级注释，标注规则来源与约束目的，便于评审核验。

### 4.3 依赖引入约束
- 禁止擅自引入第三方依赖库、框架与外部服务；新增依赖必须先通过架构决策评审并写入 ADR 文档。
- 禁止引入与 MVP 目标无关的重型框架、UI 组件库与中间件。

## 五、分支与 PR 协作规则
### 5.1 分支管理规则
- 禁止直接向 `main` 分支提交任何代码，所有变更必须通过特性分支提交 PR 评审。
- 分支命名严格遵循格式：`feature/issue-<Issue编号>-<简短功能描述>`，必须关联对应 Issue 编号。
- 单分支对应单任务，禁止在一个分支中合并多个无关需求与修改。

### 5.2 PR 提交强制要求
PR 描述必须完整包含以下内容，缺失视为无效 PR：
1. 关联 Issue 编号 + 关联 Spec 文档路径
2. 变更内容摘要：清晰说明本次修改的范围与影响
3. AI 工具使用说明：使用的 AI 工具名称、AI 完成的具体工作范围
4. 测试证据：本地构建、单元测试的验证结果
5. 风险说明：潜在影响范围与回滚方案

---

## 六、测试与质量红线
### 6.1 测试覆盖要求
- 核心业务逻辑（数字分身授权校验、对话轮次计数、审计日志生成、人工确认节点）必须配套单元测试，覆盖正常流程与异常边界场景。
- 修改业务逻辑必须同步更新对应测试用例，禁止删除已有的有效测试。
- 提交 PR 前必须在本地执行完整构建与测试，确保代码可正常运行。

### 6.2 代码质量约束
- 禁止引入已知安全漏洞、硬编码敏感信息、无效死代码与调试残留。
- 代码必须通过项目统一的格式化与静态检查，不符合规范的代码不得提交。

---

## 七、安全与数据约束
1. **隐私数据保护**：禁止在代码中硬编码密钥、凭证与用户隐私数据；用户敏感信息（学号、联系方式等）默认脱敏处理，严禁在数字分身对话中明文传输。
2. **权限校验前置**：所有数字分身操作、管理员操作，执行前必须进行权限与授权范围校验；越权操作必须直接拦截并记录审计日志。
3. **输入合法性校验**：所有用户输入、AI 生成内容必须做合法性与安全性校验，防止注入与越权操作。

---

## 八、范围管控规则
1. 严格遵循 `context.md` 定义的 MVP1 功能白名单，不得擅自实现白名单外的业务功能。
2. 需求变更必须先更新对应 `spec/` 文档与 `context.md`，再进入代码开发；禁止直接根据口头需求修改代码。
3. 技术实现不得突破已明确的 Non-Goals 边界，不得主动扩展业务范围。

---

## 九、规则生效与变更
- 本规则为项目级强制契约，所有开发人员与 AI 工具必须共同遵守。
- 规则变更需提交 PR，经小组评审通过后方可合并生效；任何个人不得私自修改本文件。
