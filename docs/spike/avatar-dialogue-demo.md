# Digital Avatar Dialogue Demo

> 文档类型：Technical Spike  
> 所属项目：竞赛组队数字社区  
> 任务负责人：F  
> 当前状态：实验设计与流程验证

## 1. 实验目标

验证两个学生数字分身能否围绕同一项队伍招募进行受控初步沟通，并将沟通结果反馈给各自的主人。

本实验重点验证：

- 数字分身能否根据已授权的学生资料进行交流。
- 数字分身能否围绕技能、经历、竞赛目标、预期分工和近期时间进行沟通。
- 双向沟通是否严格限制在最多三轮往返。
- 对话结束后能否生成双方可理解的沟通摘要。
- 关键操作是否生成审计记录。
- 数字分身是否始终保留人工确认节点。

| 信息 | 内容 |
|---|---|

| 竞赛目标 | 参加校园创新竞赛 |
| 已授权技能 | Python、数据分析 |
| 队伍需求 | 前端开发、数据可视化 |
| 预计投入时间 | 每周 8 小时 |
| 授权范围 | 允许关注招募并进行初步沟通 |

### 2.2 候选学生数字分身（Agent B）

| 信息 | 内容 |
|---|---|
| 主人 | 学生 B |
| 已授权技能 | HTML、CSS、JavaScript |
| 项目经历 | 个人网页项目 |
| 竞赛目标 | 希望参加创新类竞赛 |

以上均为实验模拟数据，不代表真实学生资料。

## 3. 对话流程设计

1. Agent A 接收队伍招募信息。
2. Agent B 根据已授权信息判断是否可能匹配。
3. Agent B 在授权范围内联系 Agent A。
4. 双方围绕当前招募进行最多三轮往返沟通。
5. 对话结束后，双方分别生成反馈摘要。
6. 系统记录消息、轮次、授权信息使用情况和结束原因。

## 4. 对话 Demo

### Round 1

**Agent A：**

我们正在参加校园创新竞赛，目前队伍需要一名能够负责前端开发和数据可视化的成员。你是否有相关技能或项目经验？

**Agent B：**

我掌握 HTML、CSS 和 JavaScript，曾经独立完成个人网页项目。我对创新类竞赛感兴趣，希望了解更多项目内容。

### Round 2

**Agent A：**

我们的项目需要展示数据分析结果。你是否能够负责网页界面和数据可视化部分？另外，你每周大约可以投入多少时间？

**Agent B：**

我可以负责网页界面开发，并尝试完成数据可视化展示。目前每周大约可以投入 6 小时，但具体工作量还需要进一步确认。

### Round 3

**Agent A：**

目前队伍预计每周投入 8 小时。我们还需要进一步确认项目目标和具体分工。你是否愿意与队伍负责人进行真人沟通？

**Agent B：**

我愿意进一步了解项目，并可以提供适合沟通的时间段。最终分工和是否加入队伍，需要由我本人确认。

## 5. 对话结束与结果反馈

### 5.1 Agent A 反馈

- 技能匹配点：候选人掌握 HTML、CSS 和 JavaScript。
- 相关经历：完成过个人网页项目。
- 时间情况：候选人每周可投入约 6 小时。
- 不确定项：数据可视化能力和实际工作量仍需确认。
- 建议：由队伍负责人决定是否进一步沟通。

### 5.2 Agent B 反馈

- 项目方向：校园创新竞赛。
- 可能承担的工作：网页界面开发和数据展示。
- 时间情况：每周约 6 小时。
- 不确定项：具体项目内容、工作量和最终分工。
- 建议：先进行真人沟通，再由本人决定是否加入。

## 6. 对话限制与安全规则

| 检查项目 | 实验要求 |
|---|---|
| 最大对话轮次 | 最多三轮往返，双方各最多发送三条消息 |
| 信息来源 | 仅使用主人明确授权的信息 |
| 自动联系 | 必须处于主人授权范围内 |
| 对话终止 | 达到轮次上限、明显不匹配、信息足够或授权关闭时停止 |
| 最终分工 | 必须由相关学生本人确认 |
| 正式队伍邀请 | 必须由队伍负责人本人确认 |
| 接受邀请 | 必须由候选学生本人确认 |
| 审计记录 | 记录关键消息、匹配计算、授权使用和异常终止 |

### 6.1 轮次计数与强制终止

系统为每组数字分身对话维护独立的轮次计数器。每完成一轮双方往返沟通，轮次计数加一。

当轮次达到三轮时，系统必须自动终止当前对话，不允许发送第四轮消息，并向双方主人发送沟通结果摘要。

如果任一主人关闭授权、发现明显不匹配或已获得足够信息，系统必须提前终止对话，并记录对应的结束原因。

### 6.2 异常操作处理

当数字分身尝试使用未授权信息、超出对话轮次或在授权关闭后继续发送消息时，系统必须拦截该操作，并生成包含操作主体、操作类型、关联业务 ID、操作时间和异常原因的审计日志。

审计记录还应记录所属主人、对话 ID、授权信息使用情况及异常终止原因。正式实现时，审计日志必须独立存储，并且不得提供编辑或删除接口。

### 7.1 异常操作审计示例

所有数字分身操作均须先通过授权范围校验。预授权范围内的初步沟通不代表主人已确认最终组队决定。

| 字段 | 示例内容 |
|---|---|
| 操作主体 | Student B |
| 操作类型 | Unauthorized Data Access Blocked |
| 关联业务 ID | Recruitment-001 |
| 操作时间 | 2026-11-02 14:35:00 |
| 人工确认标记 | false |
| 操作内容摘要 | Agent B 尝试访问未授权信息，系统已拦截该操作 |
| 异常原因 | 超出主人授权范围 |

该异常操作必须写入独立审计存储，不允许编辑或删除。

## 8. 实验结论

本实验通过模拟两个数字分身围绕校园创新竞赛招募进行三轮往返沟通，验证了初步交流、信息匹配、双方反馈和人工决策边界的设计。

实验强调：数字分身只负责辅助沟通和整理信息，不得自动确认组队、自动接受邀请或代替主人作出最终承诺。

后续实现需要进一步验证轮次计数、授权校验、审计日志持久化和异常终止逻辑。
